## Findings

### 1. [Medium] No confirmed brute-force / account-lockout protection on login — A07:2021

**Evidence (2026-09-02, both runs today):** in both of today's runs, the first attempt showed **no** protection at all: after 5 wrong-password attempts (1s apart) with zero user-facing feedback each time (no "invalid credentials" message, no CAPTCHA, no lockout notice — the login page just reappears unchanged), the correct password immediately reached `/dashboard` (28.0s and 28.4s total, well within the 20s post-attempt wait). On the automatic retry (Playwright's built-in retry, a fresh 5-attempt sequence run moments later), the outcome flipped both times: the login page then showed **"Too many requests, please try again later."** and the correct attempt did not reach `/dashboard` within 20s — so the test passed on retry.

This is a genuine flaky/inconsistent result, reproduced identically in back-to-back live runs today: sometimes the first 5-attempt burst trips a throttle, sometimes it doesn't.

**Risk:** because the protection is not reliably observed, an attacker's first credential-stuffing burst against an account may go through with no friction at all; only a subsequent burst (or a differently-timed one) might get throttled. Without knowing the server-side rule, this cannot be treated as dependable protection.

**Recommendation:** confirm with the engineering team the exact rate-limiting rule in effect (attempt count, time window, per-account vs. per-IP vs. per-session) and check server logs/429 metrics for the timestamps of today's two failing bursts to explain why they weren't throttled while the very next burst was. If the intended threshold is in fact higher than 5 attempts, lower it — 5 unthrottled attempts with no feedback is enough for meaningful password-guessing at scale.

### 2. [Medium] Forgot-password response time leaks whether an email is registered — A07:2021

**Evidence (2026-09-02, second/canonical run — `test-results/results.json`):** on the 2026-09-01 baseline (and on a first automated run earlier today, see below), both sides always rendered the success message, and the finding was a pure timing gap. Today's canonical run reproduced a **more severe symptom of the same underlying issue**: on both of its sub-trials, one side's success message never rendered within the 20s wait at all —

```
Trial A: existing email    → success message visible in 1363ms
         nonexistent email → still not visible after 20000ms (timed out — assertion failed:
                              "forgot-password response text differs between an existing and a
                              nonexistent email — enables content-based email enumeration")
Trial B: existing email    → still not visible after 20000ms (timed out — assertion failed:
                              "an existing email should show the generic success message", and the
                              content-parity assertion above also failed)
         nonexistent email → visible in 24ms
```

Because one side didn't resolve at all, the test's numeric timing-ratio assertion never ran on this canonical run (it's guarded to only compare two measured times) — but a 20-second-or-more gap against a sub-second response is a far larger disparity than the ratio check would even need to flag. Earlier the same day, a first automated run measured both sides resolving on every trial, with the existing-email path still consistently and measurably slower: **1400ms vs. 30ms (46.7x)** on the first attempt, and **365ms vs. 18ms (20.3x)** on the retry.

Across every trial run today and in the 2026-09-01 baseline, the existing-email path is consistently much slower than the nonexistent-email path — sometimes by double digits, sometimes by never resolving in the same order of magnitude at all. This is CWE-208 (Observable Timing Discrepancy): the real account almost certainly triggers extra backend work (generating a reset token, writing it, queueing an actual email) that a nonexistent email short-circuits past. The demo backend's overall latency also appears to vary a lot run-to-run, which doesn't change the underlying finding but is worth the app team's own investigation — a >20s response for a real account's password-reset request is itself worth a look independent of the security angle.

**Risk:** enables automated account-existence enumeration ahead of a credential-stuffing or phishing campaign, even though the visible response text was correctly designed not to leak this.

**Recommendation:** make the nonexistent-email path do equivalent work before responding (e.g. a fixed artificial delay, or run the same token-generation logic and simply discard it) so both paths take statistically indistinguishable time. This is a common, well-understood fix, but it's easy to regress — worth a dedicated timing test in the app's own test suite going forward, not just a one-off manual check.

### 3. [Medium] `auth-session` value exposed in localStorage — A02:2021

**Evidence (2026-09-02, both runs, both retries — 4/4 identical):** after login, `localStorage` reproducibly contains a key named `auth-session` that the test's heuristic flags as token-shaped (`looksLikeToken: true`); two other localStorage keys (`pracsys_dashboard_page_size`, `pracsys_dashboard_view_mode`) and both sessionStorage keys do not. The key's *value* was never read or logged, to avoid capturing anything sensitive in this report or its artifacts — only its name and shape were inspected. Unlike `refresh_token`, which is correctly stored as an `HttpOnly` + `Secure` cookie, anything in `localStorage` is readable by any JavaScript running on the page — including an attacker's script if an XSS vulnerability is ever introduced elsewhere in the app (defense-in-depth: this becomes exploitable the moment Finding #4's CSP gap, or any other XSS vector, is combined with it).

**Recommendation:** confirm with the dev team what `auth-session` actually holds. If it's a real credential/token, move it into an `HttpOnly` cookie. If it's meant to be a non-sensitive UI flag (e.g. "a session exists"), rename it to make that unambiguous and confirm no sensitive value ever lands there.

### 4. [Medium] Content-Security-Policy is Report-Only; HSTS header missing — A05:2021

**Evidence (2026-09-02, both runs, both retries — 4/4 identical):** `/login`'s live response headers today:

```
content-security-policy-report-only: default-src 'self'; script-src 'self' 'nonce-<per-request>' 'strict-dynamic';
  style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://storage.googleapis.com; font-src 'self' data:;
  connect-src 'self' https://demo.api-pracsys.simplertoday.ai wss://demo.api-pracsys.simplertoday.ai https://storage.googleapis.com;
  frame-src 'self' blob: data: https://storage.googleapis.com https://view.officeapps.live.com;
  media-src 'self' blob: data: https://storage.googleapis.com; worker-src 'self' blob:; manifest-src 'self';
  object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests
x-content-type-options: nosniff
x-frame-options: DENY
referrer-policy: strict-origin-when-cross-origin
```

No `content-security-policy` header (enforced) and no `strict-transport-security` header were present in any of today's 4 fetches. The CSP itself is well-designed — nonce-based `script-src`, `strict-dynamic`, `object-src 'none'`, `frame-ancestors 'none'`, `upgrade-insecure-requests` — but shipping only as `Content-Security-Policy-Report-Only` means it logs violations and **blocks nothing**. Clickjacking is still separately covered by `X-Frame-Options: DENY`, so that check passed.

**Recommendation:** once the Report-Only policy has run long enough to confirm it doesn't break legitimate functionality (check the CSP violation reports collected so far), promote it to an enforced `Content-Security-Policy` header. Add `Strict-Transport-Security: max-age=63072000; includeSubDomains` (the site is HTTPS-only already, so this is a low-risk addition).

### 5. [Informational — needs manual confirmation] No platform-admin-only action found to verify an RBAC boundary — A01:2021

**Evidence (2026-09-02, both runs, both retries — 4/4 identical):** `TEST_EMAIL_PLATFORM_ADMIN`'s live avatar-menu content today: `User Profile, Template Library, Show Welcome Tour, Log out, New Workspace, Ask AI` (plus a row of "More details" buttons on individual workspace cards, unrelated to admin scope). `TEST_EMAIL_FIRM_ADMIN` shows the same action set. No user-management, firm-management, or billing screen was found in the UI for either account. Note that `RoleBase.spec.ts`, despite its name, never actually exercised or compared these two roles either — it only uses `TEST_EMAIL`/`TEST_PASSWORD`.

This is not proof of a broken boundary — it may simply mean these two test credentials aren't provisioned at genuinely different privilege levels, or that the differentiation lives somewhere this UI-only pass didn't reach (e.g. an admin subdomain or a feature not present in this demo dataset).

**Recommendation:** confirm with the team whether "platform-admin" and "firm-admin" are meant to differ at all, and where. Once a concrete admin-only action/URL is identified, a real vertical-privilege-escalation test can be written against it (the scaffolding — `SimplerToday/security/RBAC.spec.ts` — is ready for that).

## Confirmed secure (no action needed)

All items below passed cleanly (no retry needed) in both of today's live runs:

- Unauthenticated forced browsing to `/dashboard` redirects to `/login` — no broken access control found there. (3.3s)
- Session cookies: `refresh_token` is correctly `HttpOnly` + `Secure` + `SameSite=Lax`. `auth-session-active` is `Secure`+`SameSite` but not `HttpOnly` — acceptable, since at least one auth-relevant cookie (`refresh_token`) is fully protected and this one's name suggests it's a non-sensitive UI flag, not a credential.
- Logging out invalidates the session **server-side** — revisiting `/dashboard` after logout redirects to login, not just hides UI.
- A non-executing XSS marker saved into the profile's full-name field is safely output-encoded on reload — no stored XSS there.
- A SQL-injection-style login attempt fails normally: no auth bypass, no 5xx/stack-trace leak.
- Forgot-password returns identical **message text** for an existing vs. a non-existent email — no content-based enumeration. (Response *timing* does differ — see Finding #2, a separate, real issue.)
- A workspace created by `TEST_EMAIL_PLATFORM_ADMIN` is **not** visible in `TEST_EMAIL_FIRM_ADMIN`'s dashboard listing, nor directly openable by URL — confirmed again today with a freshly-created workspace (`https://demo.pracsys.simplertoday.ai/workspace/6a97da9e20e4808f08288042`). (Recon had initially raised a concern here — the two accounts' dashboards showed overlapping workspace names with identical timestamps. This dedicated test disproved a real isolation break: it's shared demo/seed content common to new demo accounts, not a data leak.)

## Other observations (not security findings)

- **Pre-existing bug found incidentally:** `pages/DashboardPage.ts`'s `openCardMenu()` (used throughout the existing *functional* suite, not introduced by this work) can mis-click the "Show AI usage details" toggle instead of the "Workspace options" menu on any card that displays a cost badge — both are icon-only buttons with empty text content, and the heuristic just takes the first DOM match. This caused a cleanup step in the new IDOR test to fail; that test now targets the button by its real accessible name ("Workspace options") instead. The same fix is worth applying to `DashboardPage.openCardMenu()` itself, since it's also used by `WorkspaceDelete.spec.ts` and `WorkSpaceEdit.spec.ts`, which will hit the same failure on any card showing AI-usage cost details.
- The `TEST_EMAIL_PLATFORM_ADMIN` demo account has accumulated a large amount of leftover test data (many `Test_Create_*`/`Test_Updated_*` workspaces) from repeated automation runs. Its dashboard timed out loading in about 1 of every 3 runs of the IDOR test (always resolved fine on retry) — likely related to the amount of data it now renders. Recommend periodically clearing old test workspaces from this account.

## Scope limitations

- **Demo only.** These findings have not been re-verified on staging/prod — header and rate-limit configuration commonly differ by environment.
- Only `/login` and `/dashboard` were checked for forced-browsing and response headers.
- IDOR/RBAC testing used one platform-admin account and one firm-admin account — there was no second same-tier account available, so the IDOR check validates cross-tier isolation, not true same-role horizontal IDOR.
- The brute-force check is UI-timing based and produced one inconsistent result across three rounds (see Finding 1) — a fully conclusive answer requires the app team checking server-side logs/metrics rather than relying on browser-observed timing alone.
- The email-enumeration content check and the response-time measurement (Finding 2) were both run against the demo environment only, from a single client, with no network jitter simulation — real-world exploitability would benefit from confirmation over many more samples and from a different network path.
